// Linha de base do TOP-N COM HEAP contra o ORDER BY completo — 2026-08-26.
//
// Por que esta bancada existe: o caminho rápido de top-N é uma OTIMIZAÇÃO, e
// otimização sem número medido não se justifica sozinha. Ela também é o que
// fixa o teto de N do modo (tetoTopNPadrao, em internal/query/executor/topn.go)
// — o valor não foi escolhido por gosto, saiu daqui.
//
// O que ela mede: a MESMA query ligada (ORDER BY nome ASC, n DESC, LIMIT N)
// sobre o MESMO corpus, com o modo forçado pelos dois lados via
// executor.Options.TopNMax. A fonte é um dublê sem alocação nenhuma — o
// fakestorage monta e ordena um slice com todos os rowIds a cada ScanLive, e
// sobre 100 mil linhas esse custo é da mesma ordem do sort que se quer medir.
//
// Cada bancada roda uma vez FORA do cronômetro com Metrics ligado e falha se o
// modo medido não for o pedido (confereModo). A primeira rodada desta sessão
// não tinha essa guarda: o n=16.384 caiu no caminho completo dos DOIS lados —
// porque o teto padrão o recusava — e a tabela dizia "sem diferença", que era
// verdade e não significava nada. Bancada que mede o caminho errado não dá
// erro, dá um número.
//
// Três FORMAS de corpus, porque a forma decide quantas linhas o heap aceita, e
// aceitar é todo o trabalho que o modo faz além de comparar:
//   - aleatorio: permutação pseudo-aleatória, o caso realista;
//   - pior:      chave decrescente na varredura, TODA linha é aceita e despeja
//                outra — o teto de custo do modo;
//   - melhor:    chave crescente, nada entra depois das N primeiras.
//
// Como reproduzir:
//   go test ./internal/query/executor/ -run '^$' -bench BenchmarkOrdena \
//     -benchmem -benchtime=10x -count=6 | tee novo.txt
//   go test ./internal/query/executor/ -run '^$' -bench BenchmarkOrdenaCorpusCurto \
//     -benchmem -benchtime=50x -count=6 | tee novo-curto.txt
//
// Como comparar:
//   benchstat -col /caminho novo.txt
//
// Ambiente: Intel Core 7 150U (12 threads), Linux 6.8, Go 1.26.5.
//
// ------------------------------------------------------------------ LEITURA
//
// 1. SOBRE 100 MIL LINHAS O HEAP GANHA EM TODA A FAIXA MEDIDA, inclusive no
//    pior formato de dado e inclusive em N=16.384. Isso contraria a intuição de
//    que existe um N em que ele passa a perder — e é por isso que o teto NÃO
//    pode ser justificado com esta bancada sozinha.
//
// 2. QUEM FIXA O TETO É O CORPUS CURTO. Sobre 20 mil linhas varridas, N=4.096
//    (20% do varrido) ainda economiza 35% de tempo no pior formato e 59% no
//    aleatório; N=16.384 (82% do varrido) não tem diferença estatística
//    (p=0,065 nos dois formatos) e, no aleatório, a MEDIANA do heap já é pior.
//    A conta explica: o heap custa O(varrido × log N) mais uma reescrita por
//    linha aceita, o sort custa O(varrido × log varrido) mais uma cópia por
//    linha; quando N se aproxima do varrido os expoentes se encontram e sobra
//    só o sift.
//
// 3. O VARRIDO É DESCONHECIDO NO OPEN, que é quando o modo é escolhido. Então o
//    teto tem de ser um valor fixo, e o maior que ainda ganha quando o dataset
//    é pequeno. 4.096.
//
// 4. EM BYTES a economia é de outra ordem de grandeza, e é o que o modo promete:
//    801 KiB retidos em N=4.096 contra os 91,6 MiB que o caminho completo
//    materializa sobre 100 mil linhas — 117x. Em N=16.384 são 3,1 MiB, e no
//    corpus curto os mesmos 3,1 MiB contra 16,7 MiB: cinco vezes menos em vez
//    de cem. Teto que segura um quinto do dataset é quase nenhum teto.
//
// 5. ALOCAÇÕES: o heap aloca N buffers no AQUECIMENTO (25 em N=10, 4.111 em
//    N=4.096) e ZERO por linha depois disso — é o que
//    TestTopNReaproveitaOBufferDaEntradaDespejada trava por igualdade entre dois
//    tamanhos de corpus. O caminho completo aloca ~114 vezes, porque o arena
//    dobra: menos chamadas, 91,6 MiB. Contar alocações aqui engana; o que conta
//    é a coluna de bytes.
//
// 6. DISPERSÃO de 2% a 27% entre rodadas. É da máquina, não do código — use as
//    medianas do benchstat, nunca uma rodada.
//
